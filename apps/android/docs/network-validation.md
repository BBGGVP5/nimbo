# Воспроизводимая проверка сети Nimbo

Эта методика разделяет прямую доступность ноды и качество трафика через VPN. Она
нужна для проверки Nimbo на реальном Android-устройстве и для корректного сравнения с
другими клиентами.

## Подготовка

- Один телефон, одна версия Android, отключённые энергосберегающие исключения и одна
  физическая сеть на всю серию.
- Одинаковые сервер, протокол, transport и полный конфиг во всех клиентах.
- Debug APK одной зафиксированной сборки; перед серией сохранить номер версии
  `libxray.aar` и SHA-256 APK.
- Контролируемый HTTPS endpoint, журналирующий время, URI и внешний IP клиента.
- На время latency-серии отключить авторотацию. Для отдельной recovery-серии включить
  её и заранее определить основную и резервную ноды.

## Подтверждение маршрута служебной проверки

1. Подключить ноду A и проверить, что приложение показывает «Подключено» только после
   записи `Туннель ... подтверждён end-to-end запросом через VPN` в `adb logcat`.
2. На debug-устройстве проверить loopback listener:

   ```powershell
   adb shell ss -ltn | Select-String ':2080'
   ```

   Ожидается слушатель только на `127.0.0.1:2080`, не на `0.0.0.0` и не на адресе LAN.
3. Указать контролируемый endpoint как URL проверки задержки, включить «Через VPN» и
   выполнить запрос. IP в серверном журнале должен совпасть с внешним IP ноды A, а не
   с IP телефона.
4. Повторить для ноды B с другим внешним IP. Затем сделать endpoint недоступным только
   для B и убедиться, что результат B становится ошибкой.
5. Для проверки ранжирования собрать debug-вариант, в котором один из
   `TunnelHealthPolicy.serviceTargets` указывает на контролируемый endpoint. В журнале
   endpoint должны последовательно появиться IP именно проверяемых нод.

## Серия latency

Для каждого клиента выполнить не менее 30 запусков в перемешанном порядке, например
`ABCCBA`. В CSV сохранять:

```text
run,client,apk_sha256,node,network,tcp_node_ms,connect_to_first_http_ms,http_vpn_ms,external_ip,result
```

Перед зачётом каждой строки внешний IP должен совпадать с выбранной VPN-нодой.
Отдельно вычислить median, p95, p99, jitter и долю неуспешных запросов. Нельзя
сравнивать `tcp_node_ms` одного клиента с `http_vpn_ms` другого.

## Серия устойчивости

Провести и сохранить `adb logcat` для сценариев:

1. 100 последовательных подключений и отключений.
2. Wi-Fi → LTE → Wi-Fi с активным экраном и с выключенным экраном.
3. Потеря основной ноды и переход на резервную.
4. Недоступный DNS, недоступный transport и невалидный Xray JSON как отдельные причины.
5. Длительная фоновая работа не менее 8 часов.

Для каждого события фиксировать время начала, первый успешный HTTPS через VPN,
выбранную ноду и причину последней ошибки.

## Критерии приёмки

- Ни одного состояния «Подключено», если обе end-to-end HTTPS-проверки через outbound
  завершились ошибкой.
- Служебные запросы каждой ноды имеют внешний IP этой ноды.
- Один цикл подключения/ротации не превышает 60 секунд; автоматически выбранная
  нерабочая нода не проверяется повторно в течение двух минут.
- При переходе на альтернативу уведомление явно показывает имя резервного сервера.
- Listener `2080` недоступен с другого устройства в LAN.
